# dev-harness-retro

把本次对话里的坑系统整理为两类产出，让下次对话（无论哪个 AI 工具）自动读到并规避：

| 产出 | 写入位置 | 记录什么 |
|------|---------|---------|
| AI 行为约束 | `LESSONS.md` | AI 的操作失误、判断错误、流程违规——描述 AI **应该怎么做** |
| 项目领域知识 | `AGENTS.md § 15` | AI 缺乏的架构事实、排查路径、代码行为——描述项目**是什么样** |

## 适用场景

- 任何 AI 辅助任务完成后，用户想固化本次踩坑经验
- 发现 AI 重复犯了某类错误，需要建立约束规则
- 迁移到新 AI 工具前，确保项目历史教训不丢失
- 定期维护 LESSONS.md 和 AGENTS.md（去重、归档过期条目）

## 前置条件

| 依赖 | 级别 | 缺失时行为 |
|------|------|-----------|
| 项目根目录可访问（git 仓库） | ✅ 强必需 | 停止，提示用户确认项目根目录 |
| LESSONS.md（可不存在） | ❌ 可选 | 自动创建 |
| AGENTS.md（可不存在） | ❌ 可选 | 仅在有领域知识需要写入时告警，不自动创建 |

## 分流判断标准

提取出问题后，必须先判断归属，再决定写入哪个文件：

**→ 写入 LESSONS.md（AI 行为约束）**：问题的根因是"AI 做法不对"
- AI 执行了危险操作没有确认（`stop_condition`）
- AI 假设了不正确的东西（`wrong_assumption`）
- AI 用了错误的模式（`bad_pattern`）
- AI 改了不该改的范围（`scope_creep`）
- AI 用错了工具（`tool_misuse`）
- AI 违反了格式规范（`format_violation`）

**→ 写入 AGENTS.md §15（项目领域知识）**：问题的根因是"AI 不知道这个项目的某个事实"
- AI 不知道某个模块的排查顺序（架构知识）
- AI 不知道某个函数/变量的正确语义（代码语义）
- AI 不知道某个平台特性的约束（平台知识）
- AI 不知道某个路径为何存在（设计决策）

> **判断口诀**：换个项目，这条规则还适用 → LESSONS.md（行为规则）；  
> 换个项目就不适用 → AGENTS.md（项目知识）。

## 错误类型定义（用于 LESSONS.md 条目）

| 类型 | 含义 | 示例 |
|------|------|------|
| `wrong_assumption` | AI 假设了不存在或不正确的东西 | 假设文件路径存在、假设 API 返回格式 |
| `missing_context` | AI 缺乏项目特定信息导致做错 | 不知道多仓库场景、不知道某个禁改区 |
| `bad_pattern` | AI 使用了错误的方法或模式 | 用 append 写规则文件、用 grep 替代语义搜索 |
| `scope_creep` | AI 修改了不该改的内容 | 顺手重构、修改了不相关文件的编码格式 |
| `tool_misuse` | AI 用错了工具或命令 | 用 cat 读文件而不是 Read 工具 |
| `format_violation` | AI 违反了格式或风格规范 | commit message 不符合规范、注释语言错误 |
| `stop_condition` | AI 在应该停止时没有停止 | 触及高风险区未确认就继续修改 |

> ⚠️ `missing_context` 类型需特别注意：若 AI 不知道的是**项目架构事实**（排查路径、代码行为、平台约束），应写入 AGENTS.md §15，而非 LESSONS.md。只有当"缺乏的信息"描述的是 AI 的操作行为时，才写 LESSONS.md。

## LESSONS.md 格式规范

```markdown
# LESSONS — 项目级 AI 行为约束

> 由 dev-harness-retro 维护。开始任何任务前必须读此文件。
> 每条规则有历史原因，视为硬约束，不得忽略。
> 触发次数越高说明越容易重犯，优先关注。

## 活跃规则

| ID | 规则（一句话，AI 可直接执行） | 类型 | 触发次数 | 最近触发 |
|----|-------------------------------|------|---------|---------|
| L001 | 涉及多个 git 仓库时，完成报告必须输出涉及仓库表格 | missing_context | 2 | 2026-05-13 |

## 归档规则

> 超过 60 天未触发，自动移至此处。规则仍然有效，优先级低于活跃规则。

| ID | 规则 | 类型 | 触发次数 | 最近触发 | 归档日期 |
|----|------|------|---------|---------|---------|
```

**LESSONS.md ID 规则**：格式 `L` + 三位数字，从 `L001` 起递增，归档时不重用。

**LESSONS.md 规模上限**：活跃规则 ≤ 30 条，超出时归档触发次数最低且最久未触发的条目。

## AGENTS.md §15 格式规范

在 AGENTS.md 末尾维护第 15 节（如不存在则追加创建）：

```markdown
## 15. AI 导航知识（retro 沉淀）

> 由 dev-harness-retro 维护。记录通过 bug 调查发现的架构事实、排查路径和领域知识。
> 作为任务背景知识读取，不是行为规则。

### 活跃条目

| ID | 知识点（一句话，描述项目事实） | 适用范围 | 触发次数 | 最近触发 |
|----|-------------------------------|---------|---------|---------|
| K001 | Linux 显示异常排查优先检查 main.cpp 启动链中的 X11/KWin/D-Bus 调用，再进 frameless/DPI 路径 | Linux 显示/窗口 | 1 | 2026-05-14 |

### 归档条目

> 超过 180 天未触发，移至此处。

| ID | 知识点 | 适用范围 | 触发次数 | 最近触发 | 归档日期 |
|----|--------|---------|---------|---------|---------|
```

**AGENTS.md §15 ID 规则**：格式 `K` + 三位数字，从 `K001` 起递增，归档时不重用。

**AGENTS.md §15 规模上限**：活跃条目 ≤ 20 条，超出时归档触发次数最低且最久未触发的条目。归档期 180 天（领域知识比行为规则更持久）。

## 顺序化步骤

> ⚠️ **每一步必须完整执行后才能进入下一步。**

### Step 1: 定位目标文件

```
1.1 执行 git rev-parse --show-toplevel 获取项目根目录 <root>
1.2 检查 <root>/LESSONS.md：
    → 存在 → 读取全部内容，记录活跃规则数和最大 L-ID
    → 不存在 → 按格式规范创建空文件，活跃规则数 = 0，下一个 ID = L001
1.3 检查 <root>/AGENTS.md §15：
    → AGENTS.md 存在且含 "## 15." → 读取 §15 内容，记录活跃条目数和最大 K-ID
    → AGENTS.md 存在但无 §15 → 记录"需追加 §15"，最大 K-ID = K000
    → AGENTS.md 不存在 → 记录"AGENTS.md 缺失，领域知识将暂不写入"，后续 Step 3b 跳过
```

### Step 2: 回顾本次对话，提取并分流

```
2.1 系统性回顾本次对话，关注以下信号：
    - 用户纠正了 AI 的操作（"不对"、"你搞错了"、"这个不用改"）
    - AI 生成的代码/命令执行失败，需要重试
    - AI 修改了用户没有要求修改的内容
    - AI 假设了某个条件，但实际上条件不成立
    - AI 在应该停止时继续执行
    - AI 因不了解某个模块/路径/平台特性而走了弯路

2.2 对每个识别出的问题，按「分流判断标准」归类：
    → LESSONS.md：AI 行为失误（操作方式不对）
    → AGENTS.md §15：项目领域知识（AI 不知道某个事实）
    → 两者都不写：偶发性问题，无法复现，无规律

2.3 对 LESSONS.md 候选：
    - 用一句话描述规则（正向表述，AI 可直接执行）
      ✅ 正确："涉及多个仓库时必须输出涉及仓库表格"
      ❌ 错误："不要忘记多仓库" / "记得写表格"
    - 判断错误类型（见「错误类型定义」）
    - 判断是否为通用规则（见下方「通用规则判断」），标记 universal=true/false

2.4 对 AGENTS.md §15 候选：
    - 用一句话描述知识点（陈述项目事实，而非行为要求）
      ✅ 正确："Linux 显示异常排查优先检查启动链 X11/KWin 调用"
      ❌ 错误："你应该先看 main.cpp" / "记得检查 KWin"
    - 填写适用范围（如：Linux 显示/窗口、Qt frameless、合成路径）

2.5 若本次对话没有发现任何值得记录的问题：
    → 告知用户："本次对话未发现需要记录的内容。"
    → 询问是否需要执行 Step 4（维护清理）
```

> ⚠️ **HARD STOP**: 规则/知识点描述不得是模糊建议。LESSONS.md 条目必须是 AI 可直接执行的正向约束；AGENTS.md §15 条目必须是可验证的项目事实。

### 通用规则判断（仅针对 LESSONS.md 候选）

判断一条规则是否为通用规则（universal=true）：

```
满足以下任一条件即为通用规则：
① 把规则描述里的项目名、文件名、技术栈全部替换成"XXX"后，规则依然成立
   示例："git revert/force-push 前必须向用户确认" → 无论哪个项目都成立 → universal=true
   示例："涉及多个 Qt 仓库时必须输出仓库表格" → 依赖"Qt"/"仓库表格"这个具体约定 → 可能是项目级
② 规则描述的是 AI 的基本操作安全（危险命令确认、最小改动原则、不擅自扩大范围等）
③ 规则在行业内有公认的最佳实践对应

通用规则同样写入 LESSONS.md（项目级存档），但在 Step 5 中额外提示用户升级。
```

### Step 3a: 写入 LESSONS.md

```
对每条 LESSONS.md 候选规则：

3a.1 检查活跃规则表是否已有语义相同或高度相似的规则：
     → 找到匹配 → 触发次数 +1，最近触发日期更新为今天，不新增行
     → 无匹配 → 分配 L-ID，追加到活跃规则表末尾（触发次数 = 1，最近触发 = 今天）

3a.2 写入后更新 LESSONS.md 文件
```

### Step 3b: 写入 AGENTS.md §15

```
若 AGENTS.md 不存在，跳过本步骤并提示用户先运行 dev-harness-context。

对每条 AGENTS.md §15 候选知识点：

3b.1 检查活跃条目表是否已有语义相同或高度相似的条目：
     → 找到匹配 → 触发次数 +1，最近触发日期更新为今天，不新增行
     → 无匹配 → 分配 K-ID，追加到活跃条目表末尾（触发次数 = 1，最近触发 = 今天）

3b.2 若 §15 不存在，在 AGENTS.md 末尾追加整个 §15 模块，再插入条目

3b.3 写入后更新 AGENTS.md 文件
```

### Step 4: 维护清理（每次写入后自动触发）

```
4.1 LESSONS.md 归档过期规则：
    扫描活跃规则表，找出最近触发日期距今 > 60 天的规则 → 移入归档规则表

4.2 LESSONS.md 控制数量：
    若活跃规则数 > 30 → 归档触发次数最低且最久未触发的规则，直到 ≤ 30

4.3 LESSONS.md 去重：
    若两条规则语义重叠 > 80% → 合并（触发次数求和，最近触发取较新值）

4.4 AGENTS.md §15 归档过期条目：
    扫描活跃条目表，找出最近触发日期距今 > 180 天的条目 → 移入归档条目表

4.5 AGENTS.md §15 控制数量：
    若活跃条目数 > 20 → 归档触发次数最低且最久未触发的条目，直到 ≤ 20

4.6 AGENTS.md §15 去重：
    若两条知识点语义重叠 > 80% → 合并
```

### Step 5: 输出摘要

```
5.1 告知用户本次 retro 结果：

    LESSONS.md：
    - 新增规则：<ID 列表>
    - 更新规则（触发次数 +1）：<ID 列表>
    - 归档规则：<ID 列表>（若有）
    - 当前活跃规则总数：N

    AGENTS.md §15：
    - 新增知识点：<ID 列表>
    - 更新知识点（触发次数 +1）：<ID 列表>
    - 归档知识点：<ID 列表>（若有）
    - 当前活跃条目总数：N
    （若 AGENTS.md 不存在则标注：已跳过）

5.2 若本次有 universal=true 的规则，单独列出升级建议：

    ⚠️ 以下规则与项目无关，建议同时加入你的全局 AI 配置：

    - <L-ID>: <规则描述>
      → 建议加入：~/.cursor/rules/<规则主题>.md
                 或你使用的 AI 工具的全局 AGENTS.md / system prompt

    说明：这些规则已写入本项目 LESSONS.md（项目级存档），
    但若只在这里，换个项目时 AI 还是会重犯。
    加入全局配置后，所有项目均生效。

5.3 展示所有新增/更新的内容，供用户确认
    用户可在此步骤提出修改，包括调整分流归属和 universal 标记

5.4 询问是否提交两个文件：
    → 用户确认 → 建议 commit message：
                  "docs(retro): <任务简述> — LESSONS +N / AGENTS.K +N"
    → 用户跳过 → 结束，文件已在磁盘上更新
```

## LESSONS.md 的读取约定

以下文件需要声明"开始任何任务前先读 LESSONS.md"，以确保跨工具生效：

| 文件 | 位置 | 内容 |
|------|------|------|
| `AGENTS.md` | 客户端项目根目录 | 第 0 节：项目犯错记录（见下方模板） |
| `HARNESS.md` | 客户端项目根目录 | 快速验证命令之前加检查项 |
| 各 skill preamble | dev-harness 框架 | bash 段读取 LESSONS.md |

**AGENTS.md 追加模板**（由 install.py 在首次安装时注入，不覆盖已有内容）：

```markdown
## 0. 项目犯错记录（AI 必读）

开始任何任务前，检查并读取项目根目录的 `LESSONS.md`（如果存在）。
文件中每条规则均有历史原因，视为硬约束，不得忽略或覆盖。
触发次数高的规则说明 AI 在此项目中容易重犯，优先关注。
```

**各 skill preamble 追加的 bash 段**：

```bash
# 读取项目级犯错记录
_LESSONS="$(git rev-parse --show-toplevel 2>/dev/null)/LESSONS.md"
if [ -f "$_LESSONS" ]; then
  echo "=== LESSONS（项目历史 AI 犯错规则，视为硬约束）==="
  cat "$_LESSONS"
  echo "==="
fi
```

## 停止条件

- 无法确定项目根目录（非 git 仓库且用户未指定路径）
- 用户明确表示不需要记录

## 质量检验

- [ ] Step 1: LESSONS.md 已读取或已创建？AGENTS.md §15 状态已确认？
- [ ] Step 2: 本次对话已系统回顾？每个问题已按分流标准判断归属？LESSONS.md 候选已判断 universal=true/false？
- [ ] Step 3a: LESSONS.md 规则未与现有条目重复？规则描述为正向可执行约束？
- [ ] Step 3b: AGENTS.md §15 知识点未与现有条目重复？描述为可验证的项目事实？
- [ ] Step 4: LESSONS.md 活跃规则 ≤ 30？AGENTS.md §15 活跃条目 ≤ 20？过期条目已归档？
- [ ] Step 5: 摘要已输出，分流结果已供用户确认？universal=true 的规则已单独提示升级路径？
