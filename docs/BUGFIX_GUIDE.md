# BUGFIX_GUIDE

用于统一项目中 bugfix harness 的记录格式，减少 AI 与人工在复现和定位时需要读取的上下文。

## 1. Bug 描述模板

每个 bug 至少记录以下字段：

- **标题**：一句话描述问题
- **现象**：实际看到的报错、异常行为、日志或截图
- **预期**：正确行为是什么
- **影响范围**：影响哪些接口、页面、模块、用户或环境
- **首次出现时间**：可选，但推荐记录

## 2. 最小复现信息

优先记录最小必要信息，不要把无关步骤混进来：

- **环境**：版本、系统、设备、网络、开关、账号
- **前置数据**：fixture、种子数据、依赖服务状态
- **复现步骤**：按顺序列出最小步骤
- **复现命令**：能命令化就优先给命令
- **实际结果**：包括错误码、日志、截图、trace id

## 3. 调用链记录方式

定位过程中，至少沉淀以下信息：

- **入口**：接口、事件、任务、按钮、定时器或消费者
- **关键调用链**：只记录导致问题的主干路径
- **关键状态**：输入、输出、分支条件、异常点
- **缺失观测**：哪些日志、断言或埋点还不够

建议记录成固定结构：

```text
EntryPoint:
CallChain:
ObservedSignals:
MissingObservability:
RootCauseCandidates:
```

## 4. 回归测试安排

每次修复至少回答这 4 个问题：

1. 这个问题最适合在哪层验证：`quick`、`bugfix` 还是 `full`
2. 测试用例应该放在哪个目录或模块
3. 样本或 fixture 从哪里来
4. 哪个断言真正证明问题被修复

### 验证档位

授权模式决定是否允许修改和提交，验证档位只决定需要哪些证据，两者不能互相替代：

- `fast`：不超过两个生产文件的单一低风险逻辑修复，执行最小 RED 或已有失败证据、专项 GREEN、必要编译和一次差异自审。
- `standard`：存在多个受影响验证入口或中等影响范围，补齐受影响的 `quick / test / bugfix`，最终差异未变化时只校验工作区和 diff hash。
- `strict`：安全、ABI、并发、持久化、权限、签名、共享基础设施、跨仓库生产依赖或无法判断风险时，执行完整验证并按需独立审查和人工验证。

档位在问题边界确认后和最终 diff 稳定后各评估一次，只能自动升级。测试、普通 runner 和文档不计入生产文件数量；构建脚本、生成器、共享 runner 和发布配置属于共享基础设施。相同命令与相同 diff 不得无理由重复执行。

### 证据有效性与验证缺口

验证记录必须绑定执行时的内容和实际依赖。代码或相关测试变化后，受影响的旧证据失效；文档或无关依赖变化可以复用仍有效的执行证据，但仍须审查当前完整 diff。最终完成门禁同时检查根因、RED、所需验证、审查与最终内容，同阶段更新和重复 report 也适用。

必要检查因客观条件无法执行时，应记录 skip 原因、实际阻塞证据、替代验证和剩余风险，最终最多为 `DONE_WITH_CONCERNS`，不得记为通过。已有失败不能通过进入 implement、改为 skipped 或复用失败前的通过记录消除，必须由同一命令/检查的新执行通过才能清除。字段、允许的原因与证据复用规则以 [Auto Fix 契约](../auto-fix/SKILL.md) 为准。

### 恢复旧运行

Auto Fix Schema 3 分离内容指纹与暂存状态，并保存验证依赖和提交回执。旧状态迁移会清除旧审查与最终指纹，写模式撤销旧完成状态并要求重新验证、重新审查，不得把历史计划直接当作当前通过证据。

如果旧运行已经提交，且 HEAD 已不同于旧基线，应先核对已提交改动，再建立新运行；不能补造提交回执绕过校验。当前格式中 Git 已提交但回执尚未落盘的中断恢复另有精确提交校验，具体顺序见 [Auto Fix 状态与提交契约](../auto-fix/SKILL.md)。

## 5. 完成定义

一个 bugfix harness 至少满足：

- 有最小复现输入
- 有调用链或根因证据
- 已明确回归测试位置或手工验证清单
- 有可执行验证命令
- 已明确失败记录的最低要求
- 已记录验证档位、风险理由、结构化验证证据和最终 diff hash
