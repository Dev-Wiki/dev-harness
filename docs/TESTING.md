# TESTING

用于约定 bugfix harness 的分层验证方式。目标不是“多跑测试”，而是让 AI 和人工都知道每条命令分别证明什么。

## 1. 分层命名约定

推荐至少保留三层验证：

- `test:quick`
  最快反馈层，只验证当前改动最关键的基本正确性
- `test:bugfix`
  本次问题专属层，必须能覆盖对应 bug 场景
- `test:full`
  完整回归层，用于提交前或合并前确认无明显回归

如果项目不是 Node.js，也可以映射成其他命令形式，例如：

- `make test-quick`
- `pytest -m quick`
- `dotnet test --filter Quick`

关键不是命令名，而是职责固定。

## 2. 每层最少需要证明什么

### `test:quick`

- 当前改动没有立刻破坏基础路径
- 反馈时间尽量短
- 可用于高频本地迭代

### `test:bugfix`

- 明确覆盖本次问题的输入、状态或交互
- 断言必须直指问题，不得只测“周边差不多”
- 修复后应长期保留

### `test:full`

- 覆盖主干回归风险
- 在提交、合并或发布前运行
- 不要求最快，但要有明确边界

## 3. 失败输出最少标准

无论哪层失败，至少要能看到：

- 执行的命令
- 失败 case 名称
- 输入样本或上下文标识
- 预期结果
- 实际结果
- 错误码、异常栈、日志或 trace id

## 4. 推荐落地方式

项目接入 harness 时，优先做这几件事：

1. 为 quick / bugfix / full 各定义一个统一入口
2. 让 bugfix case 能单独运行
3. 把失败输出做成可读格式
4. 在 README 或开发文档中明确这些命令

## 5. 验证证据要求

任何“测试通过”“修复完成”“harness 生效”的说法，都必须基于 fresh verification evidence：

- 现跑现看
- 读完整输出
- 明确通过数量或 exit code

没有证据，不得声称完成。
